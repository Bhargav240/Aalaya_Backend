Read before you start

One blocker, one missing step

Blocker The tenant cannot verify themselves

Self-verification runs through DigiLocker, and DigiLocker is not configured — there are no DIGILOCKER_* values in your .env. I called the endpoint on your running server: POST /tenant-invitations/{id}/digilocker/start returns 500 “DigiLocker is not configured”. The app's Identity verification screen has no way past that.

The only other route from kyc_pending to verified is Manual identity review, which is a staff action — so in the current setup you verify the tenant, not the tenant. Phase 3 gives you both the honest framing and the alternative.

Working Live OTP delivery is confirmed

Codes arrive in real time through Resend from no-reply@flix89.buzz — confirmed by actually receiving them. The key, the DNS for flix89.buzz and the sender wiring all check out too, so this is settled and needs no rehearsal.

Still worth one send in the hour before you present, not to prove the feature but to catch the environmental things that do drift: a stale backend on port 8080, a dropped adb reverse, or an address that has already spent its 3-codes-per-15-minutes budget.

Correction Your flow is missing a step

You described it as: owner invites → tenant verifies → tenant logs in. There is an owner approval after verification. The tenant sits at approval_pending and cannot sign in as a tenant until you approve. That's a feature — it's the maker-checker gate — but it means the tenant's screen will look stuck if you don't know to switch back to the owner account.

The shape of it

States the invitation moves through

invited→ email_verified→ kyc_pending→ kyc_verified→ approval_pending→ approved→ active

Each arrow is enforced server-side; skipping one returns 409 with the exact transition it refused. kyc_pending is the amber step — it only exists when you tick Require identity verification, and it's the one that's blocked. Leave that toggle off and the chain runs email_verified → approval_pending directly.

Dead ends, all reachable and all worth a mention: declined and cancelled from early states, rejected from email_verified or approval_pending, kyc_failed from kyc_pending, and expired after 7 days.

Budget You get fewer logins than you think

Two accounts logging in twice each is well inside that. Rehearsing the whole flow twice back to back is not — the per-address limit is what you'll hit. Rehearse with a different address than you demo with.

Gaps — real behaviour, not what you'd assume

Do thisResultWhat actually happens
Invite an email that is already an active tenant200Accepted. No guard — a second invitation is created for someone who already lives there.
Invite the same email twice while one is pending200Both exist, and the tenant's Invites tab lists two. Avoid on stage — pick one address and invite once.
Invite onto an already-occupied bed200Accepted at create time. The conflict only surfaces at approval, when activation checks occupancy. Late, but not silent.

If someone asks whether these are bugs: the first two are missing guards worth adding, and the third is a deliberate late check — a bed can legitimately free up between invite and approval, so validating early would reject valid invitations.

Between runs

Reset so you can demo the same address twice

Rehearsing burns the address — once activated, that email is a tenant and can't be invited through onboarding again. This clears one candidate back to nothing. It touches only that address and the beds it held.

# set the address you demoed with
EMAIL='demo.tenant@example.com'

cd /home/bhargavraj/Documents/backend
set -a && . ./.env && set +a

psql "$DATABASE_URL" <<SQL
BEGIN;
DELETE FROM pool.residents
 WHERE user_id IN (SELECT id FROM platform_users WHERE email='$EMAIL');
DELETE FROM manual_kyc_reviews
 WHERE invitation_id IN (SELECT id FROM tenant_invitations WHERE email='$EMAIL');
DELETE FROM invitation_identity_verifications
 WHERE invitation_id IN (SELECT id FROM tenant_invitations WHERE email='$EMAIL');
DELETE FROM tenant_invitations WHERE email='$EMAIL';
DELETE FROM email_otps     WHERE email='$EMAIL';
DELETE FROM refresh_tokens WHERE user_id IN (SELECT id FROM platform_users WHERE email='$EMAIL');
DELETE FROM user_org_roles WHERE user_id IN (SELECT id FROM platform_users WHERE email='$EMAIL');
DELETE FROM platform_users WHERE email='$EMAIL';
COMMIT;
SQL

Deleting the resident row is what frees the bed. Clearing email_otps also resets that address's 3-per-15-min budget, which is the limit you'll actually hit while rehearsing.
